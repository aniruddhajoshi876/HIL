# MTi-680G IMU and Bosch LWS Integration Plan

Status: planning only  
MATLAB/Simulink release: **R2024b**  
Scope: MFE26 VCU firmware, inverter HIL sensor simulation, and inverter HIL GUI

## 1. Objective and end state

Add the MTi-680G IMU and Bosch F02U.V02.894-01 steering-wheel angle sensor as first-class signals across the system:

```text
MTi-680G + Bosch LWS
          |
          v
      MFE26 VCU firmware  --->  inverter HIL plant/status simulation
          |                              |
          +---------- CAN/HIL -----------+
                         |
                         v
                   R2024b operator GUI
```

The HIL deliverable must be mergeable into `master` without the bench-only
`Virtual VCU` subsystem. The real VCU will be connected to the HIL target, so
the master-branch model must receive real VCU inverter commands and transmit
simulated sensor frames to that VCU on the same verified CAN path.

The central testing principle is independent verification: the sensor
simulation is a black-box test instrument defined by the sensor datasheets,
the authoritative CAN protocol/DBC, and independently authored golden
vectors. It must not be generated by copying, calling, or reverse-engineering
the current VCU implementation. Existing VCU code is the system under test,
not the source of truth for the simulator.

This work will not claim connected-HIL or vehicle validation from host/model
tests alone. Physical CAN ACKs, wiring, termination, sensor mounting,
calibration, and signal plausibility remain separate evidence gates.

## 2. Known interface facts and open protocol gate

### Bosch LWS

The supplied Bosch datasheet defines:

- CAN speed: 500 kbit/s, Intel/LSB byte order, 100 Hz / 10 ms update rate.
- Standard frame `0x2B0`, `LWS_Standard`, five bytes.
- Bytes 0-1: `LWS_ANGLE`; byte 2: `LWS_SPEED`; byte 3: reserved plus
  `TRIM`, `CAL`, and `OK` status bits.
- A valid measurement requires `TRIM=1`, `CAL=1`, and `OK=1`.
- Failure/not-calibrated states use the documented sentinel values.
- Configuration frame `0x7C0`, two bytes: command `0x05` resets calibration and
  command `0x03` zeros the angle.
- Angle range is +/-780 degrees and absolute physical resolution is 0.1 degree.

The existing VCU driver at
`C:\Users\aniru\OneDrive - McGill University\mfe\MFE26-VC\Drivers\Device_Drivers\`
already has a partial LWS implementation, but it currently rejects all invalid
status frames without retaining health/age information and queues both
calibration messages before one transmit call. It must be reviewed and tested
before being treated as production-ready.

### MTi-680G

The supplied Xsens datasheet defines the rugged host CAN interface, 4.5-24 V
input range, 400 Hz maximum normal output rate for acceleration/rate-of-turn
and orientation data, and 2000 Hz/1600 Hz limits for the high-rate acceleration
and rate-of-turn outputs. It does **not** define the concrete CAN message IDs,
bit layout, endianness, or scaling used by the current VCU driver.

The existing driver uses standard ID `0x034`, six bytes containing three
big-endian signed `int16` values, and 1/256 m/s^2 per count. That contract must
be verified against the Xsens MT CAN Protocol documentation and the intended
MFE26 sensor DBC before it is used by the model or firmware. Unsupported or
unverified fields will remain explicitly marked as assumptions.

## 3. Phase 0 - freeze the contracts before coding

1. Locate the authoritative MFE26 sensor DBC/protocol definitions and use
   them as the simulator contract. Compare the independent contract against:
   - `MFE26-VC\Drivers\Device_Drivers\Src\MTi680G_driver.cpp`;
   - `MFE26-VC\Drivers\Device_Drivers\Src\LWSSteering.cpp`;
   - the existing HIL protocol helpers and DBC files.
2. Confirm which VCU CAN bus carries the LWS, MTi, and pedal broadcast. The
   current firmware documentation calls CAN1 the pedal/steering bus and uses
   500 kbit/s; this must be checked against the actual harness and filters.
3. Define one versioned, simulator-owned sensor contract containing CAN ID, DLC,
   signal scale/offset, valid-range rules, nominal period, timeout, and fault
   behavior for every simulated and decoded signal.
4. Define the master-branch HIL port/channel assignment for the real VCU.
   Do not copy the `Virtual VCU` Port A/channel-2 boundary into the master
   sensor-simulation change.
5. Record any unresolved MTi protocol facts in a short design note and block
   implementation of that signal until they are resolved.
6. Create golden vectors before changing the VCU. Each vector must specify
   expected wire bytes and decoded physical values independently of the VCU
   decoder, including invalid-status, stale, malformed, and unknown-ID cases.

## 5. Phase 2 - inverter HIL sensor simulation on master

Target repository: `C:\Users\aniru\OneDrive - McGill University\mfe\HIL`

### Model architecture

- Add a master-branch `Sensor Simulation` subsystem alongside the existing
  inverter HIL CAN boundary.
- It must transmit LWS and MTi frames toward the real VCU and remain
  independent of `virtual-vcu\` code, blocks, parameters, and tests.
- Keep the existing inverter model behavior: receive real VCU inverter control
  frames, simulate four inverter channels, and transmit inverter status frames.
- Put protocol encoding in code-generation-compatible functions under
  `inverter_hil\+inverterhil\`, with fixed-size frame structures and no host-only
  dependencies inside MATLAB Function blocks.
- Keep simulator protocol definitions and encoders separate from VCU source
  files. The HIL model must not include VCU firmware, call VCU decoder logic,
  or duplicate VCU internal state-machine decisions.

### Simulation controls and behavior

Expose deterministic inputs for:

- LWS angle, angular speed, calibration/trim/OK status, and frame period;
- MTi acceleration, rate-of-turn, orientation/position fields only when their
  verified CAN contract is available;
- sensor dropout, stale-frame, malformed-frame, and invalid-status injection;
- reset/zero-calibration command observation and sensor response.

The default disconnected/no-target state must show unknown telemetry, not
invented zero sensor values. In a running target application, the default
simulation should be safe and deterministic, with explicit labels indicating
that the values are simulated sensor frames.

### Test-oracle separation

- Test VCU decoding with simulator-produced bytes and independently expected
  decoded values.
- Test simulator encoding against independently authored golden bytes; never
  use the VCU decoder as the simulator's correctness oracle.
- Add mutation tests for byte order, scale, status bits, DLC, IDs, and frame
  period so accidental mirroring or permissive decoding is detected.
- Keep the protocol conformance layer reusable across future VCU revisions.

### Master-branch separation check

Before merge, verify that the model and tests contain no dependency on:

- `virtual-vcu\` source files or MATLAB paths;
- the `Virtual VCU` subsystem;
- Module 2 AI/DI loopback parameters;
- Port A/channel-2 virtual-VCU CAN writes.

The only HIL sensor path retained in master will be the real-VCU-facing sensor
simulation on the verified inverter HIL CAN channel.

### Concurrent execution requirement

The IMU and steering-sensor subsystems are independent periodic producers and
must run concurrently during every HIL step:

```text
HIL base step
   |-- inverter plant/status cycle
   |-- imu\stepImuSimulation              -> MTi CAN frame producer
   |-- steering-sensor\stepSteeringSensor -> LWS CAN frame producer
   `-- sensor scheduler/bus mux            -> deterministic CAN arbitration
```

One sensor's dropout, invalid status, or processing path must not stop, delay,
or overwrite the other sensor's frames. Nominal periods, timestamps, frame
counters, and measured rates remain independent for IMU and steering-sensor
telemetry.

### Synchronized vehicle co-simulation

Although IMU, steering sensor, and inverter frames are separate CAN devices,
the simulation must make them observations of one shared vehicle state rather
than three unrelated signal generators. In each base simulation step:

1. Apply the previous-step inverter commands and calculate the vehicle/motor
   state update.
2. Apply the steering input and calculate the corresponding kinematic state.
3. Sample the resulting state at the IMU and LWS sensor rates.
4. Encode and schedule all due CAN frames with the same simulation timestamp.
5. Publish telemetry and measured frame rates using that same timestamp.

The intended relationship is:

```text
VCU inverter commands + steering stimulus
                 |
                 v
        shared vehicle state
          |               |
          v               v
     IMU measurements   LWS angle/speed
          |               |
          +------- CAN frames -------+
                                      v
                                real VCU under test
```

The model must use a single monotonic simulation clock, explicit sample-and-
hold behavior for signals running at different rates, and deterministic frame
ordering when multiple frames are due on one step. Every frame should carry or
be logged with its source timestamp, sequence number, and simulated age.

The coupling must remain physically meaningful but implementation-independent:

- inverter torque and speed affect longitudinal/lateral vehicle state and
  therefore the IMU measurements;
- steering angle and steering rate affect the kinematic state and therefore
  lateral acceleration/yaw-rate measurements;
- the VCU receives those measurements and may change later inverter commands;
- the simulator must not call VCU control code or assume the current VCU's
  internal control algorithm to create the coupling.

Add synchronization tests for same-timestep timestamps, delayed-frame age,
different sensor rates, simultaneous frame due-times, torque-to-IMU response,
steering-to-IMU response, and dial-to-LWS-frame response. A dropout in one
sensor must not advance or retroactively alter the other sensor's state.

The steering dial must also be covered by tests for centered zero, positive and
negative limits, rate limiting, rapid movement/coalescing, disconnected-state
disablement, heartbeat fallback, and agreement between the applied virtual-car
angle and the independently encoded LWS CAN frame.

### Branch-specific model locations

- `master`: sensor simulation is connected to the real-VCU-facing CAN channel;
  no `Virtual VCU` subsystem or Module 2 loopback is required.
- `virtual-vcu`: sensor simulation is connected around the existing simulated

  remain here and are not part of the master implementation.
- Both branches must use the same simulator-owned protocol functions and the
  same golden-vector tests, with only the Simulink wiring and hardware channel
  selection allowed to differ.

## 10. Implementation roles and supervision

This work uses two explicitly assigned roles.

### Implementer

The implementer is responsible for:

- implementing the independent IMU and steering-sensor protocol layers;
- building the synchronized inverter/vehicle/sensor simulation;
- adding the steering dial and GUI telemetry;
- writing firmware, MATLAB, Simulink, and test changes in the approved paths;
- running R2024b host/model tests and firmware tests;
- documenting assumptions, failures, and evidence without overstating hardware
  validation.

The implementer may not redefine protocol fields from the current VCU code,
remove safety gates to make tests pass, or merge branch-specific `virtual-vcu`
model wiring into `master`.

### Deployed manager/supervisor

The manager must be deployed before implementation begins and remains assigned
through integration and deployment review. The manager is responsible for:

- confirming the authoritative sensor protocols and approving golden vectors;
- reviewing the architecture before implementation starts;
- supervising synchronization between inverter, IMU, steering sensor, and
  steering-dial activity;
- checking that simulation code remains independent of VCU implementation code;
- reviewing test results, generated artifacts, model paths, and branch diffs;
- approving merges into `master` and subsequent promotion into `virtual-vcu`;
- approving any target deployment or physical-HIL connection only after the
  relevant electrical, CAN, timing, and safety gates are documented.

The manager is an approval and supervision role, not a substitute for the
independent test oracle. The manager must not approve a result solely because
the simulator round-trips through the VCU decoder or because host tests pass.
